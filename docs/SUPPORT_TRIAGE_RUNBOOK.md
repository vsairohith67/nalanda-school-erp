# Support Triage Runbook

## First review

1. Verify requester identity and source without revealing whether an unrelated case exists.
2. Classify category, priority and confidentiality. Use `RESTRICTED` or safeguarding policy where required.
3. Check bounded duplicate fingerprint/reference. Link duplicates; do not merge private statements casually.
4. Route only to an eligible queue/assignee and record SLA targets.
5. Separate requester-visible messages from internal notes.

## Escalation matrix

| Case | First owner | Escalate to | Immediate control |
| --- | --- | --- | --- |
| Routine Parent/Staff question | Support operator | Principal/module owner | Acknowledge and set next step |
| High-priority operational issue | Support lead | Principal/Super Admin | Preserve logs and affected references |
| Privacy-sensitive case | Restricted support owner | Super Admin/privacy owner | Restrict participants and attachments |
| Finance integrity complaint | Finance owner | Director/Super Admin | Freeze correction; reconcile records |
| Academic integrity complaint | Principal | Super Admin | Preserve marks/report history |
| Security incident | Super Admin | Incident commander | Use first-30-minutes runbook |
| Safeguarding concern | Authorized safeguarding role | School safeguarding policy owner | Do not expose in ordinary support views |

## Closure and reopen

Resolution must state the safe outcome and corrective reference. Close only after requester-visible response where permitted. Reopen appends history; it never deletes the prior resolution. Attachments stay private and are included in governed recovery evidence.
